# SRLMM005 2026-10-21 11:10 — ENOSPC killed the gateway (disk guard + ENOSPC tolerance)

## Root cause
11:10:24.527 cron.scheduler hit ENOSPC writing ~/.hermes/cron/output; its traceback went to the
gateway's stderr pipe. The launchd wrapper `hermes_cli.stderr_timestamp` failed writing that line to
gateway.error.log (ENOSPC), raised out of main() and exited (launchd: `exited due to exit(120)`,
11:10:24.782). launchd then tore down the job and the gateway got SIGTERM (11:10:24.763, parent_pid=1),
interrupting every running kanban worker. The second SIGTERM at 11:16:34 occurred while the disk was
still full (ENOSPC logged at 11:16:34.881; macOS CacheDelete purge running 11:16:23).

## Change (branch fix/disk-guard-enospc, base 5b147ab036)
1. hermes_cli/stderr_timestamp.py: a failed log write drops the line and warns once on fd 2; the pump
   keeps draining, so the wrapper (and the gateway it supervises) survives a full disk.
2. hermes_logging.py: ENOSPC/EDQUOT handled like EIO by the managed file handler (drop + warn once,
   reopen on recovery) instead of a traceback per record.
3. gateway/kanban_disk_guard.py + dispatcher wiring: below kanban.disk_guard_min_free_gib (default 15)
   the tick still runs (reclaim/promote) with max_spawn=0; WARNING at >= kanban.disk_guard_alert_pct
   (default 90%) used, rate-limited to every 30 min. Measures HERMES_HOME's volume.
